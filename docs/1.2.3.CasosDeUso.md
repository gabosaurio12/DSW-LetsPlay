# Casos de Uso

## Actores involucrados

- **Usuario:** persona registrada y autenticada que utiliza las funcionalidades de la plataforma.
- **Administrador del canal:** usuario responsable de administrar la configuración y los permisos de un canal. Si los canales corresponden a grupos, este actor equivale al Administrador del grupo.
- **Sistema:** aplicación web encargada de mostrar las interfaces, validar la información y gestionar las solicitudes.
- **Servidor:** componente encargado de procesar las solicitudes, verificar los permisos y realizar las operaciones correspondientes en la base de datos.

---

## CU-01 — Registrar usuario

**Actor principal:** Usuario  
**Objetivo:** Crear una cuenta en Let's Play.

**Precondiciones:** La persona no debe tener una cuenta registrada con el mismo correo o nombre de usuario.

**Flujo principal:**

1. La persona abre el formulario de registro.
2. El sistema solicita nombre de usuario, correo electrónico, fecha de nacimiento, género, contraseña y confirmación de contraseña.
3. La persona captura la información.
4. El sistema valida que todos los datos cumplan las reglas definidas: nombre de usuario de máximo 12 caracteres alfanuméricos, correo válido y no registrado, y contraseñas coincidentes y seguras.
5. El sistema crea la cuenta.
6. El sistema informa que el registro fue exitoso.

**Flujos alternos:**

- **4.1.** Si falta un campo obligatorio, el sistema solicita completarlo.
- **4.2.** Si el nombre de usuario o correo ya existe, el sistema informa el conflicto.
- **4.3.** Si algún dato no es válido, el sistema muestra el error correspondiente y no crea la cuenta.

**Postcondición:** La cuenta queda almacenada y disponible para iniciar sesión.

## CU-02 — Iniciar sesión

**Actor principal:** Usuario  
**Objetivo:** Acceder a las funciones de la plataforma.

**Flujo principal:**

1. El usuario abre el formulario de inicio de sesión.
2. El usuario proporciona su correo o nombre de usuario y contraseña.
3. El sistema valida las credenciales.
4. El sistema inicia la sesión.
5. El sistema muestra el contenido disponible para el usuario.

**Flujos alternos:**

- **3.1.** Si las credenciales son incorrectas, el sistema informa que no son válidas.
- **3.2.** Si la cuenta no existe o está inactiva, el sistema impide el acceso.

**Postcondición:** El usuario tiene una sesión válida.

---

## CU-03 — Cerrar sesión

**Actor principal:** Usuario  
**Objetivo:** Finalizar la sesión activa.

**Flujo principal:**

1. El usuario selecciona la opción de cerrar sesión.
2. El sistema invalida la sesión.
3. El sistema redirige al usuario a la pantalla de acceso.

**Postcondición:** Las funciones privadas requieren iniciar sesión nuevamente.

---

## CU-04 — Cambiar contraseña

**Actor principal:** Usuario  
**Objetivo:** Sustituir la contraseña actual.

**Precondiciones:** El usuario debe tener una sesión activa.

**Flujo principal:**

1. El usuario abre el formulario de cambio de contraseña.
2. El usuario captura la contraseña actual, la nueva contraseña y su confirmación.
3. El sistema valida la contraseña actual.
4. El sistema valida las reglas de la nueva contraseña.
5. El sistema verifica que las nuevas contraseñas coincidan.
6. El sistema guarda la nueva contraseña.
7. El sistema informa que el cambio fue exitoso.

**Flujos alternos:**

- **3.1.** Si la contraseña actual es incorrecta, el sistema rechaza la operación.
- **5.1.** Si las nuevas contraseñas no coinciden, el sistema solicita corregirlas.

---

## CU-05 — Recuperar contraseña

**Actor principal:** Usuario  
**Objetivo:** Restablecer el acceso a la cuenta.

**Flujo principal:**

1. El usuario selecciona “Recuperar contraseña”.
2. El usuario proporciona su correo electrónico.
3. El sistema verifica que el correo esté asociado a una cuenta.
4. El sistema genera o envía un código o enlace de recuperación.
5. El usuario proporciona el código o utiliza el enlace.
6. El usuario captura y confirma una nueva contraseña.
7. El sistema valida la identidad y actualiza la contraseña.
8. El sistema informa que la recuperación fue exitosa.

**Flujos alternos:**

- **3.1.** Si el correo no está registrado, el sistema informa que no puede iniciar la recuperación.
- **5.1.** Si el código o enlace no es válido o expiró, el sistema solicita iniciar nuevamente el proceso.

## CU-06 — Consultar y actualizar perfil

**Actor principal:** Usuario  
**Objetivo:** Consultar y actualizar la información del perfil.

**Flujo principal:**

1. El usuario abre su perfil.
2. El sistema muestra su información actual.
3. El usuario modifica los datos permitidos.
4. El usuario selecciona entre 1 y 5 videojuegos aprobados para su biblioteca personal.
5. El usuario guarda los cambios.
6. El sistema valida y almacena la información.
7. El sistema muestra el perfil actualizado.

**Flujos alternos:**

- **4.1.** Si se seleccionan más de 5 videojuegos, el sistema impide guardar los cambios.
- **4.2.** Si se elimina la selección mínima permitida, el sistema solicita conservar al menos un videojuego relacionado.
- **6.1.** Si la imagen no cumple las reglas de formato o tamaño, el sistema rechaza la imagen.

## CU-07 — Eliminar cuenta

**Actor principal:** Usuario  
**Objetivo:** Eliminar la cuenta propia.

**Flujo principal:**

1. El usuario abre su perfil.
2. El usuario selecciona “Eliminar cuenta”.
3. El sistema muestra una advertencia y solicita confirmación.
4. El usuario confirma la eliminación.
5. El sistema elimina o desactiva la cuenta según la regla definida por el proyecto.
6. El sistema cierra la sesión.

**Flujos alternos:**

- **4.1.** Si el usuario cancela la confirmación, la cuenta permanece activa.

## CU-08 — Crear grupo

**Actor principal:** Usuario  
**Objetivo:** Crear una comunidad pública o privada relacionada con videojuegos.

**Flujo principal:**

1. El usuario abre el formulario de creación de grupo.
2. El usuario captura el nombre, la descripción y la imagen opcional del grupo.
3. El usuario elige explícitamente si el grupo será público o privado.
4. El usuario selecciona entre 1 y 5 videojuegos aprobados relacionados con el grupo.
5. El sistema valida la información.
6. El sistema crea el grupo y asigna al creador como administrador del grupo.
7. El sistema muestra el grupo creado.

**Flujos alternos:**

- **5.1.** Si el grupo no tiene entre 1 y 5 videojuegos, el sistema no permite crearlo.
- **5.2.** Si falta información obligatoria, el sistema solicita completarla.

## CU-09 — Editar grupo y videojuegos relacionados

**Actor principal:** Administrador del grupo  
**Objetivo:** Actualizar la información del grupo y sus videojuegos relacionados.

**Precondiciones:** El administrador debe tener permisos sobre el grupo.

**Flujo principal:**

1. El administrador abre la configuración del grupo.
2. El administrador modifica la información del grupo o la selección de videojuegos.
3. El sistema valida los cambios.
4. El sistema guarda la configuración actualizada.
5. El sistema muestra los cambios.

**Reglas:**

- En cualquier grupo, público o privado, deben mantenerse entre 1 y 5 videojuegos relacionados.
- El administrador puede agregar, eliminar o cambiar videojuegos relacionados.
- Solo pueden seleccionarse videojuegos aprobados.
- El administrador del grupo no puede modificar la página del videojuego.

## CU-12 — Resolver solicitud de ingreso a grupo privado

**Flujo principal:**

1. El administrador consulta las solicitudes pendientes.
2. El administrador revisa los datos del solicitante.
3. El administrador selecciona aceptar o rechazar.
4. El sistema actualiza el estado de la solicitud.
5. El sistema informa el resultado al usuario.

**Flujos alternos:**

- **3.1.** Si el administrador acepta la solicitud, el sistema registra al usuario como integrante del grupo.
- **3.2.** Si el administrador rechaza la solicitud, el usuario no obtiene acceso al grupo.

**Flujo principal:**

5. El usuario envía el reporte.
6. El sistema valida y registra el reporte con estado pendiente.

## CU-18 — Revisar reporte

**Actor principal:** Administrador de la plataforma  
**Objetivo:** Consultar y dar seguimiento a los reportes recibidos, sin aplicar sanciones.

**Flujo principal:**

1. El administrador consulta los reportes pendientes.
2. El administrador revisa el contenido reportado y la información del reporte.
3. El administrador actualiza el estado del reporte, por ejemplo: pendiente, en revisión o cerrado.
4. El sistema registra la revisión y la fecha correspondiente.

**Alcance excluido:** Este caso de uso no contempla suspensiones, bloqueos, eliminación de cuentas ni ninguna otra sanción.

**Datos por definir:** Estados finales permitidos, comentarios del administrador y notificación al usuario que realizó el reporte.

## CU-20 — Consultar perfil de usuario

**RF-98:** El *Usuario* debe poder consultar su propio perfil y los perfiles públicos de otros usuarios mediante la interacción con el sistema.

**CU-20**

**Nombre:** Consultar perfil de usuario.
**Actores:** *Usuario*.
**Descripción:** El *Usuario* consulta la información de su propio perfil o la información pública del perfil de otro usuario.
**Disparador:** El *Usuario* selecciona su perfil o el perfil de otro usuario desde la plataforma.
**Precondiciones:**
  - El *Usuario* debe tener una sesión activa.
  - El perfil que desea consultar debe existir en la base de datos.
**Postcondiciones:**
  - El perfil solicitado se muestra al *Usuario* de acuerdo con su configuración de privacidad y los permisos correspondientes.
  - No se modifica información en la base de datos.

**Flujo Normal:**
1. El *Sistema* muestra la página del perfil solicitado (ver EX01).
2. El *Sistema* envía una petición de consulta al *Servidor* con el identificador del perfil.
3. El *Servidor* consulta la información del perfil en la base de datos (ver EX02).
4. El *Servidor* verifica la configuración de privacidad y los permisos del *Usuario* solicitante (ver FA01).
5. El *Servidor* devuelve la información que el *Usuario* está autorizado a consultar.
6. El *Sistema* recibe la respuesta del *Servidor*.
7. El *Sistema* muestra la información del perfil, incluyendo los datos personales públicos, fotografía y biblioteca de videojuegos, según los permisos correspondientes.
8. Termina el caso de uso.

**Flujos Alternos:**

**FA01 - Perfil privado o acceso restringido**
1. El *Servidor* determina que el perfil pertenece a un *Usuario* con restricciones de privacidad.
2. El *Servidor* verifica si el *Usuario* solicitante cuenta con autorización para consultar el contenido.
3. Si cuenta con autorización, el flujo continúa en el paso 5 del flujo normal.
4. Si no cuenta con autorización, el *Servidor* devuelve únicamente la información permitida.
5. El *Sistema* muestra la información pública disponible e informa que el resto del contenido es privado.
6. Termina el caso de uso.

**FA02 - Perfil inexistente**
1. El *Servidor* informa que el perfil solicitado no existe.
2. El *Sistema* muestra un mensaje indicando que el perfil no está disponible.
3. Termina el caso de uso.

**Excepciones:**

**EX01 - Error al conectarse con el servidor**
1. El *Sistema* informa al *Usuario* que no fue posible establecer comunicación con el servidor.
2. El *Usuario* selecciona "Aceptar".
3. Termina el caso de uso.

**EX02 - Error en la base de datos**
1. El *Servidor* informa que ocurrió un error al consultar la información.
2. El *Sistema* informa al *Usuario* que no fue posible recuperar el perfil.
3. El *Usuario* selecciona "Aceptar".
4. Termina el caso de uso.

**Reglas de negocio:**
- El *Usuario* únicamente podrá consultar la información privada de su propio perfil.
- La información de otros perfiles deberá mostrarse de acuerdo con las restricciones de privacidad establecidas.
- Los perfiles privados no deberán exponer información restringida a usuarios no autorizados.

**Inclusiones de CU:** N/A.
**Extensiones de CU:** N/A.

## CU-21 — Editar perfil de usuario

**RF-99:** El *Usuario* debe poder consultar y actualizar la información personal de su perfil mediante la interacción con el sistema.

**CU-21**

**Nombre:** Editar perfil de usuario.
**Actores:** *Usuario*.
**Descripción:** El *Usuario* modifica la información personal asociada a su perfil.
**Disparador:** El *Usuario* selecciona "Editar perfil" desde su perfil.
**Precondiciones:**
  - El *Usuario* debe tener una sesión activa.
  - El *Usuario* debe tener un perfil previamente creado (CU-01: Registrar usuario).
**Postcondiciones:**
  - La información del perfil queda actualizada en la base de datos.
  - Los cambios realizados se reflejan al consultar nuevamente el perfil.

**Flujo Normal:**
1. El *Sistema* muestra el formulario de edición del perfil (ver EX01).
2. El *Sistema* recupera y muestra la información actual del *Usuario*.
3. El *Usuario* modifica los campos que desea actualizar.
4. El *Usuario* selecciona "Guardar cambios".
5. El *Sistema* recopila los datos y valida que sean válidos (ver FA01).
6. El *Sistema* envía una petición de tipo PUT al *Servidor* con la información actualizada (ver EX01).
7. El *Servidor* verifica que el *Usuario* tenga autorización para modificar el perfil.
8. El *Servidor* actualiza la información correspondiente en la base de datos (ver EX02).
9. El *Servidor* devuelve una respuesta al *Sistema*.
10. El *Sistema* informa al *Usuario* que su perfil fue actualizado correctamente.
11. Termina el caso de uso.

**Flujos Alternos:**

**FA01 - Datos inválidos**
1. El *Sistema* identifica que uno o más campos contienen información inválida.
2. El *Sistema* informa al *Usuario* qué campos deben corregirse.
3. El *Usuario* corrige la información.
4. El flujo regresa al paso 4 del flujo normal.

**FA02 - Cancelar edición**
1. El *Usuario* selecciona "Cancelar".
2. El *Sistema* descarta los cambios que no hayan sido guardados.
3. El *Sistema* muestra nuevamente el perfil sin modificaciones.
4. Termina el caso de uso.

**Excepciones:**

**EX01 - Error al conectarse con el servidor**
1. El *Sistema* informa al *Usuario* que no fue posible establecer comunicación con el servidor.
2. El *Usuario* selecciona "Aceptar".
3. Termina el caso de uso.

**EX02 - Error en la base de datos**
1. El *Servidor* informa que no fue posible actualizar la información.
2. El *Sistema* informa al *Usuario* que ocurrió un error al guardar los cambios.
3. El *Usuario* selecciona "Aceptar".
4. Termina el caso de uso.

**Reglas de negocio:**
  - El *Usuario* únicamente podrá modificar la información de su propio perfil.
  - Los campos obligatorios deberán contener información válida.
  - Los cambios deberán validarse tanto en el *Sistema* como en el *Servidor*.
  - Los datos que identifican de manera única una cuenta deberán respetar las reglas de unicidad establecidas.
**Inclusiones de CU:** N/A.
**Extensiones de CU:** N/A.

## CU-22 — Administrar fotografía de perfil

**RF-100:** El *Usuario* debe poder agregar, consultar, reemplazar y eliminar la fotografía asociada a su perfil mediante la interacción con el sistema.

**CU-22**

**Nombre:** Administrar fotografía de perfil.
**Actores:** *Usuario*.
**Descripción:** El *Usuario* administra la fotografía de su perfil, pudiendo agregar una nueva imagen, reemplazar la existente o eliminarla.
**Disparador:** El *Usuario* selecciona la opción para administrar su fotografía desde la edición de su perfil.
**Precondiciones:**
  - El *Usuario* debe tener una sesión activa.
  - El *Usuario* debe contar con un perfil previamente creado.
**Postcondiciones:**
  - La fotografía queda almacenada, actualizada o eliminada según la operación realizada.
  - El perfil refleja el estado actual de la fotografía.

**Flujo Normal:**
1. El *Sistema* muestra la fotografía actual del *Usuario* y las opciones disponibles (ver EX01).
2. El *Usuario* selecciona la operación que desea realizar: agregar, reemplazar o eliminar fotografía.
3. El *Sistema* procesa la operación seleccionada (ver FA01 y FA02).
4. El *Sistema* envía la solicitud correspondiente al *Servidor* (ver EX01).
5. El *Servidor* verifica que el *Usuario* tenga autorización para modificar la fotografía.
6. El *Servidor* realiza la operación correspondiente sobre la fotografía almacenada (ver EX02).
7. El *Servidor* devuelve una respuesta al *Sistema*.
8. El *Sistema* actualiza la vista del perfil.
9. El *Sistema* informa al *Usuario* que la operación se realizó correctamente.
10. Termina el caso de uso.

**Flujos Alternos:**

**FA01 - Agregar o reemplazar fotografía**
1. El *Sistema* muestra el selector de archivos.
2. El *Usuario* selecciona una imagen desde su dispositivo.
3. El *Sistema* valida el formato, tamaño y tipo del archivo (ver FA03).
4. El *Sistema* prepara la imagen para enviarla al *Servidor*.
5. El flujo continúa en el paso 4 del flujo normal.

**FA02 - Eliminar fotografía**
1. El *Sistema* solicita confirmación para eliminar la fotografía actual.
2. El *Usuario* confirma la operación.
3. El flujo continúa en el paso 4 del flujo normal.
4. Si el *Usuario* cancela la operación, el *Sistema* conserva la fotografía actual y termina el caso de uso.

**FA03 - Archivo inválido**
1. El *Sistema* detecta que el archivo no cumple con el formato o tamaño permitido.
2. El *Sistema* informa al *Usuario* el motivo del rechazo.
3. El *Usuario* selecciona otra imagen.
4. El flujo regresa al paso 3 de FA01.

**Excepciones:**

**EX01 - Error al conectarse con el servidor**
1. El *Sistema* informa al *Usuario* que no fue posible establecer comunicación con el servidor.
2. El *Usuario* selecciona "Aceptar".
3. Termina el caso de uso.

**EX02 - Error al almacenar o eliminar la imagen**
1. El *Servidor* informa que no fue posible completar la operación.
2. El *Sistema* informa al *Usuario* que ocurrió un error al modificar la fotografía.
3. El *Usuario* selecciona "Aceptar".
4. Termina el caso de uso.

**Reglas de negocio:**
  - El *Usuario* únicamente podrá modificar la fotografía de su propio perfil.
  - Solo se permitirán los formatos de imagen aprobados por el sistema.
  - El tamaño máximo de archivo deberá respetar los límites establecidos.

## CU-37 — Consultar notificaciones

**RF-115:** El sistema deberá permitir que un usuario consulte las notificaciones asociadas con los eventos relevantes de su cuenta dentro de la plataforma.

**CU-37**

**Nombre:** Consultar notificaciones.
**Actores:** *Usuario*.
**Descripción:** El *Usuario* consulta las notificaciones generadas por los eventos de la plataforma que estén asociados con su cuenta.
**Disparador:** El *Usuario* selecciona la opción "Notificaciones" desde la navegación principal.
**Precondiciones:**
  - El *Usuario* debe tener una sesión activa.
**Postcondiciones:**
  - El sistema muestra las notificaciones disponibles para el *Usuario*.
  - Las notificaciones conservan su estado de lectura o no lectura, salvo que se defina expresamente otra regla.

**Flujo Normal:**
1. El *Sistema* solicita al *Servidor* las notificaciones asociadas con el *Usuario* (ver EX01).
2. El *Servidor* identifica las notificaciones correspondientes a la cuenta.
3. El *Servidor* recupera la información de las notificaciones.
4. El *Servidor* devuelve las notificaciones al *Sistema*.
5. El *Sistema* muestra las notificaciones en orden cronológico, indicando cuáles han sido leídas y cuáles permanecen pendientes de lectura.
6. El *Usuario* consulta las notificaciones disponibles.
7. Termina el caso de uso.

**Flujos Alternos:**

**FA01 - Sin notificaciones**
1. El *Servidor* determina que el *Usuario* no tiene notificaciones registradas.
2. El *Sistema* informa al *Usuario* que no existen notificaciones disponibles.
3. Termina el caso de uso.

**FA02 - Notificación relacionada con contenido no disponible**
1. El *Usuario* selecciona una notificación cuyo contenido relacionado ya no está disponible o cuyo acceso está restringido.
2. El *Sistema* informa que el contenido ya no puede consultarse.
3. El *Sistema* conserva la notificación de acuerdo con las reglas de almacenamiento aplicables.
4. Termina el caso de uso.

**Excepciones:**

**EX01 - Error al conectarse con el servidor**
1. El *Sistema* informa al *Usuario* que no fue posible establecer comunicación con el servidor.
2. El *Usuario* selecciona "Aceptar".
3. Termina el caso de uso.

**EX02 - Error al recuperar las notificaciones**
1. El *Servidor* informa que ocurrió un error al consultar las notificaciones.
2. El *Sistema* informa al *Usuario* que no fue posible cargar las notificaciones.
3. El *Usuario* selecciona "Aceptar".
4. Termina el caso de uso.

**Reglas de negocio:**

  - Un *Usuario* únicamente podrá consultar sus propias notificaciones.

## CU-38 — Marcar notificación como leída

**RF-116:** El sistema deberá permitir que un usuario marque como leída una notificación pendiente de lectura asociada con su cuenta.

**CU-38**

**Nombre:** Marcar notificación como leída.
**Actores:** *Usuario*.
**Descripción:** El *Usuario* cambia el estado de una notificación pendiente para identificar que ya consultó su contenido.
**Disparador:** El *Usuario* selecciona una notificación no leída o utiliza la opción "Marcar como leída".
**Precondiciones:**
  - El *Usuario* debe tener una sesión activa.
  - Debe existir una notificación asociada con la cuenta del *Usuario*.
  - La notificación debe encontrarse pendiente de lectura.
**Postcondiciones:**
  - La notificación queda registrada como leída.
  - El sistema actualiza el indicador de notificaciones pendientes, cuando corresponda.

**Flujo Normal:**
1. El *Sistema* muestra la lista de notificaciones del *Usuario*.
2. El *Usuario* selecciona una notificación no leída.
3. El *Sistema* envía una solicitud al *Servidor* para actualizar el estado de la notificación (ver EX01).
4. El *Servidor* verifica que la notificación pertenezca al *Usuario* solicitante.
5. El *Servidor* verifica que la notificación se encuentre pendiente de lectura.
6. El *Servidor* actualiza el estado de la notificación en la base de datos (ver EX02).
7. El *Servidor* devuelve una respuesta al *Sistema*.
8. El *Sistema* actualiza el estado visual de la notificación.
9. El *Sistema* actualiza el indicador de notificaciones pendientes.
10. El *Sistema* informa al *Usuario* que la notificación fue marcada como leída.
11. Termina el caso de uso.

**Flujos Alternos:**

**FA01 - Notificación previamente leída**
1. El *Servidor* determina que la notificación ya se encuentra marcada como leída.
2. El *Sistema* conserva el estado actual de la notificación.
3. El *Sistema* informa al *Usuario* que la notificación ya había sido consultada.
4. Termina el caso de uso.

**FA02 - Notificación inexistente**
1. El *Servidor* determina que la notificación no existe o ya no está disponible.
2. El *Sistema* informa al *Usuario* que no fue posible localizar la notificación.
3. Termina el caso de uso.

**Excepciones:**

**EX01 - Error al conectarse con el servidor**
1. El *Sistema* informa al *Usuario* que no fue posible establecer comunicación con el servidor.
2. El *Usuario* selecciona "Aceptar".
3. Termina el caso de uso.

**EX02 - Error al actualizar la notificación**
1. El *Servidor* informa que no fue posible actualizar el estado de la notificación.
2. El *Sistema* informa al *Usuario* que ocurrió un error al modificar la notificación.
3. El *Usuario* selecciona "Aceptar".
4. Termina el caso de uso.

**Reglas de negocio:**
  - Un *Usuario* únicamente podrá modificar el estado de lectura de sus propias notificaciones.
  - Una notificación leída no deberá volver automáticamente al estado de no leída.
  - El cambio de estado no deberá eliminar la notificación ni el evento que la originó.
  - El sistema deberá actualizar los indicadores de notificaciones pendientes de acuerdo con el estado almacenado.
**Inclusiones de CU:** N/A.
**Extensiones de CU:** N/A.

### Consideraciones para la implementación

1. Las operaciones de seguimiento, bloqueo y silenciamiento deberán validar los permisos y las relaciones existentes en el *Servidor* antes de modificar la base de datos.
2. Las relaciones entre usuarios deberán tener restricciones que eviten registros duplicados.
3. El bloqueo deberá tener prioridad sobre las demás interacciones sociales: no se permitirá seguir, consultar contenido restringido ni intercambiar mensajes entre cuentas bloqueadas.
4. El silenciamiento deberá ser independiente del seguimiento y del bloqueo.
5. La configuración de privacidad de los grupos deberá aplicarse en las consultas al *Servidor*, no únicamente mediante restricciones de visualización en la interfaz.
6. Los cambios de privacidad de un grupo no deberán eliminar sus publicaciones ni sus integrantes.
7. Las relaciones de seguimiento pendientes deberán distinguirse de las relaciones aceptadas.
8. Los cambios de estado deberán reflejarse en la interfaz únicamente después de recibir una respuesta satisfactoria del *Servidor*.
